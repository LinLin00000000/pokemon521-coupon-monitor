# 提取方案与访问边界

## 1. 无 Token 的实际测试

### 通知频道 `@pokemon521`

使用普通 HTTPS GET：

```text
https://t.me/s/pokemon521
https://t.me/s/pokemon521?before=<最老帖子编号>
```

公开 HTML 中可以稳定观察到：

- `data-post="pokemon521/<id>"`
- `<time datetime="...">`
- `.tgme_widget_message_text`
- `.tgme_widget_message_photo_wrap` 的公开图片 URL
- 某些消息的反应数和浏览数

第一次页面约有 18 个帖子；使用 `before` 分页后，v1 的一次扫描拿到了 83 条可见帖子。83 不是固定上限，取决于频道当时可通过公开预览返回的历史深度。

当前测试的 `pokemon521/395` 页面能够得到正文和图片，但没有得到公开评论/讨论消息节点。即使 Telegram 客户端里存在评论区，也不能据此推断 `t.me/s` 页面能匿名读取评论。

### 交流群 `@pokemon_love`

以下两个公开 URL 都能返回 HTTP 200：

```text
https://t.me/pokemon_love
https://t.me/s/pokemon_love
```

但后者解析后会回到群组简介页；两者都没有 `data-post` 消息节点。它们能提供群名、成员数、在线人数和关联频道等简介信息，不能提供可分页的聊天历史。

因此 v1 的结论是：

```text
频道：匿名公开历史可读
交流群：匿名简介可读，匿名聊天历史不可用
```

这里没有创建账号、加入群组、启动机器人、调用 Telegram API，也没有用浏览器 Cookie 绕过这个边界。

## 2. 方案对比

### 方案一：字符串/规则匹配

处理链路：

```text
公开频道 HTML
  -> 帖子 ID / 时间 / 正文 / 图片 URL
  -> 兑换码标签正则
  -> 规范化与去重
  -> current-month / historical 分层
  -> latest.json + history.jsonl
```

适合当前项目的原因：

1. 频道正文中的明确码可以稳定抽取，例如 `兑换码：xxx`。
2. “兑换码藏在图片”可以准确判断为需要人工复核，而不是猜测。
3. 不需要模型 Token、额外服务或 Python 大依赖。
4. 结果有可复现的帖子链接和发布时间。
5. GitHub Actions 的权限、网络请求和提交内容都很小。

主要缺点是：无法仅凭规则恢复图片中的隐藏文字，也不能从当前不可见的交流群历史中获得线索。

### 方案二：近百条记录 + AI 小模型

理论链路：

```text
抓取可见消息窗口
  -> 过滤与截断
  -> AI 输出严格 JSON
  -> 代码校验候选格式、来源和月份
  -> 人工兑换
```

它只能改善“已经拿到的文字内容”的理解能力，不能解决两个前置问题：

- 没有公开预览的交流群消息，AI 无法凭空读取；
- 图片中的码需要 OCR/视觉输入，普通文本小模型不能解决。

它还会增加：

- 模型 API Key 或本地模型安装；
- 调用费用、限流和重试；
- 非确定性和幻觉候选；
- 将 Telegram 正文或图片发送给第三方的隐私和平台条款风险；
- 输出 JSON 校验、模型漂移和供应商故障处理。

## 3. 当前决策

v1 采用“规则优先 + 图片线索人工确认”：

- 近百条公开频道消息用于召回；
- 只保存相关信号，不保存完整聊天记录；
- 明文码才进入 `candidates`；
- 图片线索进入 `manual_review`；
- 旧月份候选只写入 `history.jsonl`，不进入当前 `latest.json`；
- 不实现 AI 调用适配器，避免为尚未证明的收益引入长期结构税。

## 4. 何时值得加入 AI

只有出现明确的实际信号才升级，例如：

- 连续多个月的有效码都只出现在很短的自然语言谜面中；
- 规则链路有可统计的漏检样本，且这些样本可以由已公开文本复现；
- 人工复核成本已经高于维护一个可控模型适配器的成本；
- 已经决定模型供应商、数据边界、Token 存储方式和失败回退。

即使触发升级，也应先添加离线 fixture 和可选 adapter，不应把 AI 直接放进默认公共 Actions 主链路。
